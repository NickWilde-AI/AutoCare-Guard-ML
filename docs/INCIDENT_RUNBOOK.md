# 线上事故复盘 Runbook

这份文档用于回答“线上出问题你怎么处理”。售后风险研判模型最怕的不是离线分数低，而是上线后误升级、漏判、延迟、上游特征污染和路由链路异常。

## 1. 总体处理原则

先止血，再定位，再回滚或修复，最后复盘和回流样本。

1. 降低处置强度：暂停 `emergency_review` 自动流转，全部进人工确认。
2. 切换兜底：流量切回上一模型或规则引擎。
3. 固化现场：保存请求、模型输出、版本、特征、路由和人审反馈。
4. 定位原因：按输入、模型、后处理、策略、上游服务逐层排查。
5. 修复验证：离线回放事故样本，再 shadow 灰度。
6. 回流样本：把确认的误判样本进入 refinement 池。

## 2. 事故一：紧急动作误判突然升高

现象：

- `emergency_review_rate` 高于历史基线（告警阈值见 `configs/default.yaml`）。
- 人审驳回率升高。
- 客诉或申诉成功率升高。

止血：

- 紧急动作全部改为人工确认。
- 小流量切回 shadow。
- 保留信息回复、补采和服务跟进，避免研判链路完全失效。

排查：

- 看 `vehicle_signal_summary` / `fault_evidence` 是否异常偏多或字段被写错。
- 看 `missing_vehicle_evidence_rate` 是否异常。
- 看 `model_version / rubric_version / postprocess_version` 是否变更。
- 抽样看 raw output 是否出现格式异常或过度判高。
- 对比规则引擎和上一版本模型输出。

常见根因：

- 上游车辆 / 故障服务默认值写错。
- 新 rubric 过严。
- 合成数据高风险样本占比过高。
- 后处理把普通工单动作错路由成紧急确认。

修复：

- 修上游特征或回滚特征版本。
- 降低紧急路由条件，强化车辆侧证据门禁。
- 回放事故样本，补充“高风险但证据链不完整不紧急”的 hard sample。

## 3. 事故二：漏判高风险车辆事件

现象：

- P0/P1 工单复盘中模型判无风险。
- 规则命中但模型未命中。
- 巡检、救援复盘或人审发现漏判。

止血：

- 对强规则主题恢复规则优先。
- 对相关 `event_topic` 提高召回阈值。
- 将可疑样本进入人审队列。

排查：

- 对话证据是否被截断。
- 车辆信号 / 故障证据是否未聚合。
- prompt 是否选错 topic rubric。
- 模型是否对新型故障表述不敏感。

修复：

- 补短证据列表训练样本。
- 更新 rubric 与车辆侧模式。
- 加入 hard sample refinement。
- 新增上游召回规则或故障异常类型。

## 4. 事故三：JSON 解析失败率升高

现象：

- `parse_non_ok_rate` 升高。
- 兜底比例上升。
- raw output 多解释文本、缺字段或格式损坏。

止血：

- 启用正则兜底。
- 解析失败默认信息回复或进入规则兜底。
- 暂停依赖模型直接处置的链路。

排查：

- 是否修改 prompt 或 JSON Schema。
- 是否打开 sampling。
- `max_new_tokens` 是否过小导致截断。
- 模型 checkpoint 是否切错。

修复：

- 恢复贪心解码。
- 固定字段顺序。
- 增加格式坏例到 SFT。
- 必要时启用 grammar constrained decoding，但要评估延迟。

## 5. 事故四：P95/P99 延迟超预算

现象：

- vLLM queue time 升高。
- P95 超过 1.2s。
- GPU 显存或 KV cache 压力升高。

止血：

- 限流或降级部分低风险流量到规则。
- 缩短 max_new_tokens。
- 临时扩容实例。

排查：

- 输入 token 是否变长。
- prefix cache 是否失效。
- QPS 是否超过容量规划。
- 是否有异常长证据列表。
- tensor parallel 或 batch 参数是否变更。

修复：

- 恢复 prefix caching。
- 控制证据截断策略。
- 增加实例。
- 对强规则样本做分层路由，减少大模型调用。

## 6. 事故五：车辆侧证据大量缺失

现象：

- `missing_vehicle_evidence_rate` 升高。
- 模型更多依赖对话文本，mid_risk 准确率下降。
- 工单 / 紧急动作占比异常波动。

止血：

- 缺车辆侧证据样本不允许直接 `emergency_review`。
- 进入规则兜底、补采或人审。

排查：

- 车辆 / 故障特征服务是否超时。
- 上游数据表是否延迟。
- 字段 schema 是否变更。
- 默认值是否被清空或写成字符串。

修复：

- 恢复特征服务。
- 增加字段 schema 兼容。
- 缺车辆侧证据时使用保守 prompt 和保守路由。

## 7. 复盘模板

每次事故复盘至少记录：

- 事故时间线。
- 影响范围：请求量、车辆数、工单数。
- 触发指标：紧急误判率、解析失败率、延迟、客诉等。
- 涉及版本：model/prompt/rubric/feature schema/postprocess。
- 根因：输入、模型、后处理、策略、上游服务中的哪一层。
- 止血动作。
- 长期修复。
- 回流样本数量和训练计划。

## 8. 处置原则

将问题区分为输入、模型、解析、策略和服务异常。先通过强处置转人工或切回规则基线止血，再结合版本与审计日志定位变化，最后仅将确认并脱敏的误判样本进入后续 refinement 流程。
